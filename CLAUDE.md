# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Hardcover Desktop is a Linux desktop client for [hardcover.app](https://hardcover.app). It is written in Rust (edition 2024) with gpui-kit 0.10. The licence is MIT, and the app id is `io.github.alisayyah.HardcoverDesktop`.

## Commands

```sh
cargo run -p hardcover-desktop                    # run the app (signs in with OAuth, or restores the keyring session)
cargo run -p hardcover-desktop --features demo    # a sample library: no account, keyring, settings or real cache; writes stay in memory; only covers are downloaded
HARDCOVER_DEMO_FAULTS=latency=800ms,500,error-rate=0.2 cargo run -p hardcover-desktop --features demo   # the demo, slow and failing on request (below)
HARDCOVER_GALLERY=1 cargo run -p hardcover-desktop --features demo   # the shared components (ui/) in their states, on one page
cargo test --workspace                            # unit tests; live-API tests are #[ignore]d
cargo test -p hardcover-core <name>               # one test, e.g. `unauthorized_refreshes_once_and_retries`
cargo clippy --workspace --all-targets
cargo fmt --all

# Live API: needs network and a token
HARDCOVER_TOKEN=... cargo test -p hardcover-core --test live_read -- --ignored
HARDCOVER_TOKEN=... cargo run -p hardcover-core --example smoke   # read-only
cargo run -p hardcover-core --example oauth_login                 # CLI sign-in, stores the session in the keyring
cargo run -p hardcover-core --example oauth_check -- <book-id>    # scope + write cycle on a book NOT in the library
cargo run -p hardcover-core --example api_check                   # check the live API for changes; updates schema/
cargo run -p hardcover-core --example api_check -- --check        # same, without writing; exit 1 on any change
```

A build without `demo` runs once per data directory (`instance`): with the installed app running, `cargo run -p hardcover-desktop` shows that window and exits. The demo build, or a run with its own `XDG_DATA_HOME`, runs beside it.

The `justfile` wraps these; `just` lists the recipes.
- `just check` runs fmt-check, clippy (`-D warnings`, also over the demo build, which CI does not) and the tests.
- `just ci` adds `cargo deny`, the packaging validation, ShellCheck (`just shellcheck`), the release script's test (`just release-test`), the apt wrapper's test (`just apt-test`) and actionlint.
- `just package` builds the release tarball into `target/package/`; `just appimage` repacks it as an AppImage and its `.zsync`, next to it. An AppImage bundles the build system's libraries, so a release one is built on Ubuntu 22.04.
- `just demo-faults <faults>` runs the demo with `HARDCOVER_DEMO_FAULTS` set, e.g. `just demo-faults scope=read:goals`.
- `just api-check` is `api_check --check`; `just schema-update` is the run that rewrites `schema/`.
- `just release patch` makes a whole release, from the PR to the published GitHub release (below, under CI and releases).
- Only the live-API recipes load `.env`; `just run` never does, so a token there can't bypass OAuth.
- The recipes that write to the real account, and `oauth-login`, ask for confirmation.

Keep the justfile in step when a command here changes.

Debug builds compile dependencies without debug info (`[profile.dev.package."*"]` in `Cargo.toml`), which halves `target/` and keeps parallel worktrees small; our own crates keep it. To step into a dependency in a debugger, or see its line numbers in a backtrace, pass `--config 'profile.dev.package."*".debug=true'`.

`api_check` is local only and is not run in CI. It uses `HARDCOVER_TOKEN` if set, otherwise the app's keyring session; both see the same schema. It does three things:
1. Introspects the live schema and lists added, removed and changed types and fields.
2. Validates every document in `queries::ALL` against the live schema.
3. Checks the public scope map (`https://api.hardcover.app/capabilities.json`): every scope in `auth::DEFAULT_SCOPES` must still exist, and together they must grant every top-level field, gated column and gated argument the documents use. Some scopes gate only arguments: `write:reviews` grants no operation, just the `review*` fields of `insert_user_book`/`update_user_book`. Arguments inside a variable's value can't be seen statically, so an ungranted one there is a note, not a failure. The same check runs offline against `schema/` in the unit tests (`the_requested_scopes_cover_every_document`).

It then rewrites `schema/hardcover.graphql` and `schema/hardcover-capabilities.json`; review the change with `git diff schema/`. It exits non-zero if a document breaks or a scope no longer covers it. Never edit `schema/` by hand.

Environment variables (see `.env.example`; `.env` is gitignored and must never be committed):
- `HARDCOVER_TOKEN`: a personal access token. For development only: it bypasses OAuth in the app, and the examples and live tests use it.
- `HARDCOVER_CLIENT_ID`: overrides the compiled-in OAuth client id, `auth::DEFAULT_CLIENT_ID`. Its session has its own keyring entry (`KeyringTokenStore::for_client`), so a refresh token is only ever sent by the client it was issued to.
- `HARDCOVER_THEME=light|dark`: forces a theme, over the choice in Settings, which then shows it as unavailable.
- `HARDCOVER_GALLERY=1` (demo build only): opens the shared components' gallery (`ui::gallery`) instead of the app.
- `HARDCOVER_DEMO_FAULTS` (demo build only): faults the demo injects, comma-separated (`demo::Faults`, whose doc is the reference):
  - `latency=800ms` (or `2s`) delays every request.
  - `offline`, `timeout`, `429`, `401` and `500` say how requests fail; `offline` and `timeout` fail cover downloads too. The 429 carries a `Retry-After` of 60 s, longer than the client retries by itself, so it shows as the rate-limit error at once.
  - `error-rate=0.2` fails that share of requests, picking one of the listed failures each time (`500` if none is listed); without it every request fails. `writes` limits the failures to mutations.
  - `scope=read:goals` takes the scope out of the demo's grant (features hide or disable as for a session without it) and refuses every request that needs it with `insufficient_scope`; `refuse=read:goals` keeps it in the grant and only refuses, as when Hardcover is the one to say no. What a request needs is the scope map's (`faults::required_scopes`, checked against `schema/hardcover-capabilities.json` by a test), so a scope that gates no field there, such as `read:social`, can only be taken out of the grant. The "Sign in again…" notice needs a `Session`, which the demo has not, so it never shows.
  - `vibes=unbuilt`: the reader's Recommendations and Top Picks exist but were never built (no books), as for a reader who never opened Discover on hardcover.app; `vibes=none`: the reader has none yet, so the app's `ensure_system_vibes` makes them, unbuilt.
  - Unknown items are reported on stderr and nothing is injected.
- `HARDCOVER_NO_UPDATE_CHECK=1`: turns off automatic update checks, whatever Settings says. Debug builds never check on their own; "Check for updates" (account menu, or Check now in Settings) always works.
- `HARDCOVER_UI_SCALE=<k>`: forces the interface scale (`ui_scale`), from 0.5 to 3; `1` turns the automatic scale off and reads no outputs. There is no Settings control for it. `HARDCOVER_UI_SCALE_DEBUG=1` logs the outputs read and every factor chosen.
- `live_writes` example: `HARDCOVER_LIVE_WRITES=yes`, `HARDCOVER_LIVE_PHASE`, `HARDCOVER_TEST_BOOK_ID`.

Live write tests run against a real account. Restore everything afterwards. Removing a book does not delete its `reading_journals` rows; clean those up separately, which needs a token with journal scope.

## Architecture

The workspace has two crates, in `crates/*`.

**`hardcover-core`** has no GPUI dependency, and every call in it is **synchronous and blocking**: there is no async runtime.
- `api`: `Client` over the GraphQL endpoint `https://api.hardcover.app/v1/graphql`.
  - `queries.rs` holds every GraphQL document as a const. A unit test validates each one against `schema/hardcover.graphql`, an introspected SDL loaded through apollo-compiler.
  - When you add or change a query, register it in `queries::ALL` so the test and `api_check` cover it. `api/sdl.rs` holds the validator; `api_check` includes the same file through `#[path]`, because apollo-compiler is a dev-dependency.
  - `wire.rs` holds the raw response shapes; `model.rs` holds the public types. Book and series descriptions and author bios go through `markup::plain_text`: Hardcover sends some as publisher HTML (`<p>`, `<i>`, `&amp;`), which becomes paragraphs split by a blank line; text with no block tags keeps its own line breaks, and only known HTML tags count (`<https://…>` stays). Checked live, read-only: 14 of about 1,300 descriptions and bios had tags (11 of the library's 812 books), none mixed block tags with blank-line paragraphs, and none kept a tag or entity after it.
  - `UserBookFields` (the sync and every library write) includes the book's `book_series`, so an entry knows its series without a book page, and whether the book is a compilation of the series (`SeriesRef::compilation`: a boxed set or omnibus, whose position is its books'); the series tracker and Home's Up next leave compilations out, as Hardcover's series lists do. Checked live: a full sync of about 800 entries took under 5 s with it. The sync asks for 500 entries a page (`LIBRARY_PAGE_SIZE`): live, on 834 entries, that was 2 requests and 1.3 s against 9 and 3.6 s at 100 (measured before the empty request that now ends every sync, so 3 requests today), and leaves most of the rate limit's burst to the rest of startup. 1,000 a page was slower (one request of 3.2 s).
  - Paging (`keyset_pages`, `offset_page`): keyset pages (the library, lists, list memberships) stop only on an empty page, never on a short one: Hardcover caps `lists` and `list_books` at exactly the page sizes used, so a lower cap would otherwise end a list early, silently. That costs one empty request at the end; asking for an `_aggregate` count instead would cost more, since Hardcover charges a rate-limit token per top-level field (each document has exactly one). Offset pages (a list's books, editions, reviews) ask for one row more than a page (so a full last page isn't taken for more; a server cap below that would read as the end, but none is known) and return `OffsetPage { items, next_offset, has_more }`; `next_offset` counts the rows Hardcover sent, so a row whose book didn't resolve neither ends the list nor shifts the next page.
  - `Client::library` returns `LibrarySync { entries, coverage }`. A row whose book is null or whose status is unknown is dropped, not the page, and listed in `Coverage::Complete { unreadable }`; `Coverage::Partial` (paging stopped moving forward) vouches for nothing it didn't return. `LibrarySync::merged_with` keeps the previous copies of both, and the library model replaces the cached library only after a complete sync (a partial one only upserts), so a sync never deletes on the strength of rows it couldn't read or reach.
  - It also includes the book's `default_audio_edition_id` (`LibraryEntry::book_audio_edition`, for the progress dialog's "Choose an audiobook edition…": checked live, read-only, Hardcover set it on 625 of 834 entries, and no book without it had an audiobook edition, where `books.audio_seconds` was set on 16) and each edition's `reading_format_id`. `LibraryEntry::measure` (and the core's `ProgressContext`, through the same `measure_of`) says what progress is counted in and the length in that unit: the first of the open read's edition and the entry's edition that says decides the unit, else the book's pages. An audiobook edition (`reading_format_id` 2) counts time, even with a page count, and only by its own running time: without one `length()` is `None` and a percentage can't be converted. Any other known format counts pages, taking the next page count (another page edition's, else the book's) when it lists none, so a read on a paper edition never counts time because the entry's edition is an audiobook. The book's own `audio_seconds` is never a unit. Caches from before the id have the format's name ("Listened"), which counts too.
  - `Client::tracked_series` (`SERIES_OVERVIEW`, `read:catalog`) asks for the started series with every book, 25 series per request (`TRACKED_SERIES_BATCH`), at most 200 rows each. Compilations, merged duplicates and books with no position are filtered in the query and again in `wire.rs`. A failed batch doesn't throw the others away: `TrackedSeriesLoad` holds what loaded, the ids of failed batches (`missing`) and the first error. Only an error about that batch (`Api`, `Decode`) lets the rest go on; a network, session, scope or rate-limit failure would repeat, so the batches not sent yet count as missing; the series model keeps the previous copy of each missing series and shows the failure beside the rows. Not yet checked live: how long a request of 25 large series takes.
  - `Client::trending_books(period)` asks for the ranked ids (`BOOKS_TRENDING`), then the books with their `book_series` (`TRENDING_BOOKS`: `BOOKS_BY_IDS` plus the series, as `BOOK_DETAILS` asks for them), as `TrendingBook { book, series }`, so Discover can show one book per series. Not checked live: how much the series add to the request's time.
  - Vibes (`read:vibes`): `Client::system_vibes` (`SYSTEM_VIBES`: the user's Recommendations, `vibe_type` 1, and Top Picks, 3), `featured_vibes` (`FEATURED_VIBES`, the 12 Hardcover features most recently) and `vibe(id)` give `Vibe`s, whose `book_ids` are `cached_book_ids` in Hardcover's ranked order (`wire::vibe_book_ids` reads it leniently: duplicates and non-positive ids go) and whose `built_at` is `books_generated_at`. `vibe_books(ids, offset)` reads a page of those books through `BOOKS_BY_IDS`, 25 at a time (`VIBE_BOOKS_PER_PAGE`), in the vibe's order; `next_offset` counts the ids asked for, so a book that didn't resolve doesn't shift the next page. `ensure_system_vibes` and `exclude_from_vibe` (`write:vibes`) are the writes; `exclude_from_vibe` reads the vibe first (`VibeById`, a write step) and sends its title, description and privacy back with the exclusion (below, under the API quirks).
  - Tags (`read:catalog`): `BOOK_DETAILS` also asks for `taggable_counts` of the 26 vote tags (`tags::VOTE_TAG_IDS`: the 14 moods, 3 paces, 3 drives, 6 character tags), so `BookDetails::votes` holds the exact counts behind the mood line; `cached_tags` stays for the genres, warnings and other tags. `Client::books_by_tag(tag, within, offset)` (`BOOKS_BY_TAG`, or `BOOKS_BY_TAG_WITH` when `within` narrows it: two documents, since a `where` passed whole as a variable hides its fields from the scope check) is a tag's page, `TAG_BOOKS_PER_PAGE` (50) at a time as an `OffsetPage<TagBook>`, each book with its votes for the tag, ordered by `count`, then `taggable_id` (the tiebreak keeps offset pages stable; not verified live). `Client::book_tags(ids)` (`BOOK_TAGS`) is a shelf filter's batch: per book the genres of `cached_tags(path: "Genre")` merged into `BookGenres` and the 14 moods' votes only (`BookTags::moods`; a pace row is dropped, so its mood line names no pace), `BOOK_TAGS_BATCH` (100) books a request, a failed batch handled as `tracked_series` handles one (`BookTagsLoad`; both go through `in_batches`). Checked live by the owner, read-only: 36 books and their `cached_tags` in one `books` request took 1.6 s.
- `http.rs`: a small transport seam. Production uses ureq. `http::fake::FakeTransport` scripts responses for the tests in `api/tests.rs`.
  - All fixtures must be synthetic: no real user data.
  - `HttpRequest` deliberately does not implement `Debug`, because it carries tokens.
- `ratelimit.rs`: a client-side token bucket with burst 8 and a refill of 1 per second. Hardcover's own limits are 60 requests per minute, burst 10, and at most 10 top-level fields per request.
  - Two priorities, each a FIFO lane: `Priority::Interactive` callers are admitted before any waiting `Background` one. The client classifies requests itself (`Client::priority_of`): every mutation, every search and the reads that are steps of a write (`WRITE_STEP_READS`: the progress context, read-backs, the row an edit reads first) are interactive whatever the client's priority, so no call site can forget; other reads go at the client's priority (`Client::with_priority`, `Background` by default).
  - A 429 is a block, not a debt: no request goes out before `max(blocked until, now + Retry-After)`, and callers already waiting wake and respect a later block. A block over `LONG_BLOCK` (60 s: the daily limit) is remembered, and every call fails at once with `Error::RateLimited { retry_after }` until it ends. The throttled request is retried once, only if the retry can go out within 15 s (`MAX_AUTO_RETRY_WAIT`), queue included.
  - A mutation that timed out after it may have been sent, or got a 504, fails with `Error::OutcomeUnknown` ("may have been saved") and is never retried. A resolve or connect timeout (10 s each) is a definite `Error::Network`. Not covered: a connection reset after the request went out is still a plain `Network` error.
  - On a 401 it calls `TokenSource::on_unauthorized` once, which refreshes the token, then retries.
- `auth`: OAuth for a native public client.
  - Authorization code with PKCE S256, redirected to a loopback `http://127.0.0.1:<port>/callback`. `state` and `iss` are checked. A request without this sign-in's `state` gets a 400 and the wait goes on (any local program or web page can send one); each connection has 3 s in all for its request head, and Cancel is checked while it reads. A Cancel that lands during the code exchange revokes the new tokens.
  - `Session` stores tokens in the system keyring (`KeyringTokenStore::for_client`: `keyring-core` with its D-Bus Secret Service store, one entry per OAuth client) and refreshes them proactively. Entries are found by `service` and `username`; keyring 3 (up to 0.4.0) also set `target = "default"`, and each version finds, updates and deletes the other's entries (checked against a real Secret Service when moving to keyring-core), so an update signs nobody out. The connection is made on first use and kept; a failed one is tried again next time. Refresh tokens are single-use, and the app, a second copy, the examples and `api_check` all share the entry, so (`auth/session.rs`'s doc has the details):
    - A refresh holds the session's lock and the store's cross-process `flock` (`TokenStore::lock`: `$XDG_RUNTIME_DIR/hardcover-desktop/<account>.lock`, else the data directory). Under it the store is read again, and a token another process rotated is adopted instead of refreshing. A failed lock is logged and the refresh goes on: the re-read is what protects the tokens, also against an older version that takes no lock.
    - Only `invalid_grant`, `invalid_client` and `unauthorized_client` (`oauth::DEAD_GRANT`) sign a session out. Any other failure, including a 4xx without an OAuth `error` (a captive portal's or proxy's page), is transient, and a token still in date keeps working. The store is cleared only if it still holds the rejected token (or one this session spent); a newer one there is adopted.
    - A rotated pair is used at once. If saving it fails, the call still succeeds and the save is tried again on a later call, at most every 30 s; the session remembers the refresh tokens it spent, so the stale one left in the store is never adopted.
    - `Session::start` revokes tokens it can't save, so a sign-in on a broken keyring leaves no live grant. A keyring that can't be read at startup (`Startup::KeyringUnavailable`) shows "Try again" on the sign-in screen, not a new sign-in; an entry that doesn't decode counts as none. Before opening the browser, both sign-ins check the keyring (`KeyringTokenStore::check_available`, a throwaway entry beside the tokens).
  - `StaticToken` is the `HARDCOVER_TOKEN` path.
  - Scopes: `DEFAULT_SCOPES` is `read:me read:catalog read:library write:library write:reviews read:goals write:goals read:lists write:lists read:journal read:social write:social read:users read:notifications write:notifications read:vibes write:vibes`; the names are constants in `auth::scopes`. Adding one makes every existing session show the "sign in again" notice, so add new scopes in batches. `GrantedScopes` checks a grant, following the scope map's `implies` (`read:lists` covers `read:lists:public`; `all` covers everything); a test keeps its table in step with `schema/hardcover-capabilities.json`.
  - The granted scope is recorded with the tokens. A code exchange whose response has no `scope` records the requested scopes (RFC 6749 §5.1); a refresh without one keeps the recorded scope. Tokens with no recorded scope were saved by 0.1.x and count as `LEGACY_SCOPES` (the four it requested).
  - `Session::replace` swaps a new sign-in's tokens into the existing session (the "sign in again" path), so every `Client` on it moves to them. Never start a second `Session` next to a live one: its refresh would write the old grant back over the new one. The old grant is not revoked. `replace` refuses once the session is signed out, so a sign-in that finishes late can't sign the user back in; `Session::discard` revokes tokens nobody will use.
- `store`: `LibraryCache`, a SQLite database at `~/.local/share/hardcover-desktop/library.sqlite3` (WAL, `synchronous=NORMAL`: it is a cache). A sync's `replace_library` writes only the rows whose JSON changed and deletes the rest, so a sync that changes nothing writes one row (the sync time).
  - It holds private notes: the file and its WAL are 0600 (an existing file is made so), `secure_delete` is on, and `clear` (sign-out) checkpoints and truncates the WAL and deletes a `.damaged` file, so nothing of the library stays readable in the files. `clear` fails if another instance keeps the WAL open.
  - A file that isn't a database, or fails `PRAGMA quick_check` at open, is moved to `library.sqlite3.damaged` (one kept) and a new cache is made.
  - Beside the library it keeps what the app's other models fetch (goals, lists, the list membership index, upcoming books, tracked series, the shelves' book tags) in a `companions` table, as JSON per kind and key (`save_companion`, `load_companions`, `remove_companion`): the last good copy, shown at the next launch and offline. The system and featured vibes are kept there too. It isn't keyed by account: the cache holds one, and `clear` (sign-out, an account mismatch) removes the companions too. A row that no longer decodes is skipped.
- `covers`: `CoverCache`, on disk at `~/.cache/hardcover-desktop/covers`. It downloads, asking for and accepting only the types the app shows (`DECODABLE`; another is `Error::Decode`, before anything is written), and syncs only SVGs, the downloads the app keeps; the app keeps scaled copies and deletes the rest (below), so `cached_path` being `None` doesn't mean a cover isn't cached. `file_path` is where a download goes.
- `demo` (the `demo` feature, and in tests): `demo::client()` answers every GraphQL operation from `demo/catalogue.json` through a fake transport, so queries, parsing and paging run as they do against Hardcover. `demo::client_with(&faults)` injects `HARDCOVER_DEMO_FAULTS` (above) in that transport; `client()` injects none, for the tests.
  - The demo is writable. Each client holds its own copy of the reader's library, reads, reviews, lists and goals (`demo/state.rs`), seeded from the catalogue; every mutation changes it and answers in Hardcover's shape (`demo/writes.rs`), so `LibraryModel::write`, `merge_sync`, the review generations and the list and goal writes run in the demo. Nothing is saved: the next run starts from the catalogue again. The writes follow the API quirks below; what is unverified (adding a book already in the library is refused; moving to Read with no open read adds a read finished today; a new read takes the entry's edition) is listed in `writes.rs`. A mutation sending a field the demo doesn't write is refused, so a new field isn't silently dropped; when you add a mutation, handle it in `writes::apply` (`every_write_is_answered` checks the list).
  - Every date of the reader's (added, updated, read started and finished, reviewed; other readers' reviews too) is a number of days from today, resolved when the client is built, so the demo always looks current: the books being read were updated in the last week except Atomic Habits (idle on purpose), Middle Earth hasn't been touched for over a year, two books finished lately are unrated (so "Rate what you finished" shows), and one was finished today, so the goal counts it even on Jan 1. The goal is the current year's, dated as Hardcover dates its year goals (Jan 1 to Jan 1), its progress counted from the reads. Tests pin the date (`Clock::Fixed`).
  - It covers the awkward cases: audiobook editions (`reading_format` 2) with and without a running time, an entry read as an audiobook (progress in seconds) and one whose read moves to the audiobook edition; The Cruel Prince, with no page count, two non-featured series and the book's own `audio_seconds` (the only catalogue book Hardcover gives one); every entry read on paper whose book has an audiobook edition offers "Choose an audiobook edition…" (the demo names its first audiobook edition as the default, as Hardcover does); a compilation (The Lord of the Rings) on its series pages; a book in two series; a fractional position on a shelf (Edgedancer, 2.5); a Read book with no read; a Paused book with an open read; an audiobook edition on the Owned list. Tags: each catalogue book has its real votes (`votes`, tag id to count) and its genres' real votes, from Hardcover's public catalogue (`demo/tags.rs`): Ulysses (14 mood votes) has no mood line, Edgedancer names Fast and The Fellowship of the Ring Slow; on Want to Read, three Science Fiction books are Reflective and four Fantasy ones Adventurous, so the shelf filter has something to combine; Klara and the Sun's "Sci-fi" adds to its "Science Fiction"; Edgedancer keeps only Fantasy (its other genres have a vote or two). Tag pages rank the catalogue by those votes. A genre on the Browse list answers to its Hardcover id; every other genre name has a demo id from 90,001 (`GENRE_IDS`), each spelling its own tag, as on Hardcover. Upcoming books have no tags.
  - Series and author pages and similar books are derived from the catalogue, with the demo's own author and series ids. Books have no ratings distribution or alternative titles: the catalogue does not record them. A book's real editions come from Hardcover; a book with none listed has one stand-in edition with the book's id, title and cover. `demo::cover_cache()` passes only the catalogue's cover and edition cover URLs, and the reviewers' avatars (Hardcover's generic default avatars, `static/avatars/profileN.png`, never a user's picture), through to the real network, and refuses every other URL.
  - The books are real popular ones; their ids, facts, editions and cover URLs come from Hardcover. The descriptions are our own short text, not publisher blurbs. The reader, their shelves and their lists (an Owned list and three others) are invented: no real users.
  - Covers are downloaded from Hardcover at runtime, only for the catalogue's own URLs. Never commit the images.
  - When you add a query, give it an answer in `demo::answer`; the `every_document_has_an_answer` test fails until you do. Mirror the document's `where` and `order_by`, so the demo doesn't show what Hardcover wouldn't send.
  - `upcoming` holds a few unreleased books in the catalogue's series, for "Coming soon": placeholder titles like Hardcover's ("Untitled Empyrean #4"), ids from 99,000,001 (far above the catalogue's), no cover and no description (never invent one for a real series' unreleased book). Each date is `days` from today, so the demo never goes stale; keep one within two weeks, so Home's card shows. They answer `UpcomingInSeries` and `BookDetails`, and are on their series pages; "Want to read" can add one to the shelf.
  - `follows` (`demo/follows.rs`): the reader follows seven series (Stormlight, Dune, Middle Earth, Reidverse, Mistborn, The Martian, The Empyrean), each followed some days ago; Elfhame and The Folk of the Air (being read) are not followed, so the Series nudge shows, and two series only on Want to read are left for Add series. Following an unknown series is an error; following one again returns the same follow.
  - `vibes` (`demo/vibes.rs`): the reader's Recommendations (id 501, 11 books) and Top Picks (502, 8; Children of Dune is left out of both, so Discover's "Because you loved Dune" has a book: the demo's similar books are its catalogue, almost all in the library), built yesterday (`built_days_ago`), and three featured vibes owned by invented curators. `update_vibe` writes only the fields `exclude_from_vibe` sends, refuses a vibe of someone else's, and takes an excluded book off the vibe's ids at once (Hardcover's own timing is unknown). `vibes=unbuilt` and `vibes=none` (above) show the states before Hardcover builds them.
- `tags`: the community tags, pure and tested.
  - `Mood` (the 14 that count, with id, name, slug and `site_votes`, Hardcover's `tags.count` read live on 2026-11-22), `Pace`, `Drive` and `CharacterTrait`/`TraitPair` (the review form's character tags). `BookVotes` holds a book's counts for them, built from `(TagId, count)` pairs; a tag with no row counts 0.
  - The mood line (`mood_line`): no line under 50 mood votes (`LINE_MIN_MOOD_VOTES`). A mood stands out with at least 10% of the book's mood votes and a lift (its share over its site share, the site share being its `site_votes` over `SITE_MOOD_VOTES`) of at least 1.5; the line names the standouts by lift, at most 3, else (`fallback`) the 3 most voted. The pace is Fast or Slow when it leads with at least 20 pace votes and holds half of them; never Medium. `rarely`: only among the ten most used moods (`RARELY_MOODS`: Challenging, Inspiring, Informative and Relaxing are never named), a lift of at most 0.2, by site votes, at most 3, and only from 100 mood votes (`RARELY_MIN_MOOD_VOTES`). Ties go to the most voted, then the lowest tag id. Integer arithmetic throughout. `has_mood` is the shelf filter's test and is the line's own (a book filtered by a mood shows it). `breakdown` is the "Votes" popover: moods with at least 5 votes, Rarely, the pace and drive splits from 20 votes (`Split`, in scale order, with its `leader`), and a character pair from 20 votes when one side holds two thirds (`CharacterLean`). Every threshold is a named constant.
  - `tags/tests.rs` runs the rule on 36 real books (`tags/fixtures/`: Hardcover's public catalogue counts, read 2026-11-23, and expected lines worked out independently), all 28 of the demo's among them.
  - Genres (`tags/genre.rs`): `genre_words` (lowercase words; `&` is "and", apostrophes go, other punctuation separates; `chip::genre`'s icons use it too) and `genre_key`, which also reads "sci fi"/"scifi" as "science fiction" and "non fiction" as "nonfiction"; "Science Fiction & Fantasy" stays a genre of its own. `BookGenres::from_tags` merges a book's spellings by key, adding their votes, named after the most voted spelling, and leaves out a genre under 3 votes (`MIN_GENRE_VOTES`). `BROWSE_GENRES` is Discover's Browse list with Hardcover's genre tag ids; `browse_genre(name)` finds the one a spelling belongs to (`cached_tags` names a genre without its id).
- `instance`: one running app per data directory. `main` claims `instance.lock` (a `lock::FileLock`) in `~/.local/share/hardcover-desktop/` and listens on `instance.sock` beside it; a later launch finds the lock taken, asks the running copy to show its window, and exits. The running copy calls `activate_window`; on Wayland the compositor may only mark it as wanting attention. The demo build never claims it, so it runs beside a real one; so does a run with its own `XDG_DATA_HOME`.
- `prefs`: `Preferences` (theme, automatic update checks, the books left out of a vibe (`vibe_exclusions`)) in `~/.config/hardcover-desktop/settings.json`. Loading never fails: a missing or garbled file gives the defaults, and each field is read on its own (`Deserialize` is written by hand), so one an older version didn't write, or holding a value a newer one did, takes its default while the others keep theirs. Add a new field there too. Writes are atomic (temporary file, then rename). The file survives signing out.

**`app`** (the package is named `hardcover-desktop`) is the GPUI UI.
- `main.rs` sets up actions, keybindings and the window.
- `ui_scale/`: the automatic interface scale. On a large monitor the interface is drawn `k` times larger than the design, `k` from 1 to 1.5 in eighths, by setting the rem to `16 * k` px: `design::theme::set_ui_scale` rebuilds both theme configs with that `font_size` (and the kit's radii), which gpui-component's `Root` sets as the window's rem, so the factor holds through every later `Theme::change`. All design sizes are design px; anything built from rems follows. There is no Settings control: `HARDCOVER_UI_SCALE` forces a factor.
  - The policy (`policy.rs`, pure, tested): a logical pixel must subtend at least the angle of one on a 24" 1080p monitor at scale 1, seen from a distance of 145 + 1.65 × the shorter side in mm (clamped to 400–1000 mm). The owner's 27" 4K at 1.5 gets 1.25, their 16" 2560×1600 laptop at 1.6 gets 1. No size, a tiny one, an aspect ratio stored as mm (160 × 90) or a TV (taller than 70 cm) gets 1.
  - Facts: GPUI drops the outputs' millimetres, so `wayland.rs` opens a second connection on `WAYLAND_DISPLAY`'s socket (never `WAYLAND_SOCKET`, GPUI's) and reads each `wl_output`'s name, mm and current mode and its `zxdg_output_v1` logical size, in about 1 ms. Reads run off the UI thread: the first on a thread started at the top of `main` (which waits for it at most 250 ms before opening the window), the others in `background_spawn`. Any failure gives 1.
  - Which monitor: only an output whose own scale (mode ÷ logical size, long side to long side, so rotation doesn't matter) is `window.scale_factor()` qualifies; GPUI's display (a v5 uuid of the `wl_output` name) when it qualifies, else the one output that does, else the factor stays. It is worked out again on bounds and display changes, but only applied when (output, scale) changes; a display change reads the outputs again.
  - X11 gets 1. RandR has the monitors' mm, but GPUI's X11 bounds are inside the window manager's frame, so finding the window's monitor would mean asking the X server on every move, and with no logical sizes the window couldn't open at its design size. Left until someone runs the app on X11 with a large monitor.
  - Window sizes: the window opens at 1200 × 800 and its minimum is 800 × 560, both times `k` (`policy::opening`), worked out before it exists from the first read: the default at the largest output's factor, the minimum at the largest factor of any output, both within the smallest output's logical size. GPUI sets the minimum only when a window opens, and resizing a window after it lands doesn't work on Hyprland (it keeps a floating window's size; GPUI then draws the new size inside the old frame), so a window that moves to a monitor with another factor keeps its size. A forced factor reads no outputs, so its sizes aren't bounded by a monitor.
  - Anything that keeps a px size across frames must be keyed by the rem: the shelf and search splits (`h_resizable`) are, so a new factor starts them again at their default width; the series tracker's list sizes are part of its `ListKey`. A `WrappingText::width` or `TextButton::wrap_width` takes px at the window's rem (`Rems::to_pixels(window.rem_size())`), never `px(design)`.
  - Verified on Hyprland only; not on GNOME or KDE.
- `session.rs`: `SessionScope`, one sign-in's scope: the client, the OAuth `Session`, the library cache, the granted scopes and an alive flag. The `Shell` builds it on signing in and the `Workspace` hands it to the models it creates (`LibraryModel`, `GoalsModel`, `ListsModel`, `FollowsModel`, `UpcomingModel`, `SeriesModel`, `Reauthorize`); it is also installed as a global for views, found with `SessionScope::current(cx)` (an `Option`: never a panicking lookup).
  - Every account call goes through `SessionScope::run` (`interactive` for writes, searches and pages the user opened; `background` for syncs, reloads and prefetches), which runs it on the I/O threads (`io.rs`) with `Client::with_priority` set to the same lane. It resolves to `None`, and the call never runs, once the session has ended; a result landing after that is `None` too. Callers only return on `None`. Models check `allows(scope)` (alive and granted) before starting work, so a timer or Refresh firing during sign-out sends nothing.
  - It owns the library cache's worker (`library/cache_worker.rs`), a thread of its own: reads and writes run in the order they were sent, from every model (`cache_write`), so a sync's replace can't delete a row a later upsert wrote, and sign-out's clear (`clear_cache`) runs after every write and takes the worker away, so nothing is written after it.
  - Signing out (`Workspace::sign_out`) ends the session first, then `LibraryModel::end_session` drops the sync, the writes and the review fetches and clears the cache (library and companions) as the last job of its worker, then revokes; `SignedOut` waits for both. A later sign-in reuses the same `LibraryCache` and starts empty.
  - Scopes: views ask `session::has_scope(cx, scopes::READ_GOALS)` (false once signed out); it is cheap enough for `render`. The grant is shared by every clone, so a model's own handle sees "Sign in again…"'s new grant; `session::observe_grant` hears of it. Never ask the `Session` for its scope from the UI thread: its lock is held across a token refresh. A personal token (`HARDCOVER_TOKEN`) counts as having every scope, and so does the demo, less any `scope=` in `HARDCOVER_DEMO_FAULTS`.
  - A feature whose scope is missing hides, or shows a disabled state with `format::needs_permission`. A session that lacks any of `DEFAULT_SCOPES` gets the sidebar notice (`sign_in/reauthorize.rs`): "Sign in again…" first finds out whose session it is (`me()` if the library doesn't know yet), runs the browser sign-in, checks that the same account approved (another account's tokens are revoked, as are those of a sign-in cancelled meanwhile), and calls `Session::replace`; the cache and the library stay. Signing out cancels a sign-in still waiting on the browser. Turn a failed request into a message with `SessionScope::error_message` (or `session::error_message` in a view), not `format::error_message`: on `insufficient_scope` it records the refused scope (`SessionScope::scope_refused`, which counts it as missing) so the notice appears, and otherwise says to sign out and in again.
- `app_state.rs`: how the app starts, and the cover service:
  - `CoverService` (from `cover_pipeline`) lives for the whole run.
  - `startup()` picks the auth path in this order: `HARDCOVER_TOKEN`, then the keyring session, then the sign-in screen. A keyring that can't be read gives the sign-in screen's "Try again" state (`restore_session` again).
  - With the `demo` feature, `startup()` always returns the demo client with an in-memory cache, before anything real is opened, with the faults and grant `HARDCOVER_DEMO_FAULTS` asks for (`demo::env_faults()`, read once). Covers go to a temporary directory, and preferences are not saved.
- `io.rs`: where blocking work runs. Every core call runs on the I/O threads, never on the UI thread or GPUI's background pool (as many threads as cores, shared by everything: a few calls stalled on the network or sleeping in the rate limiter held it), and its result is applied on the foreground. Account calls go through `SessionScope::run`; the rest (startup, the sign-in's keyring checks, the update check, saving preferences) through `io::run` or, fire and forget, `io::spawn`.
  - Four `core-io` threads, two FIFO lanes (`Priority`): an interactive job runs before any waiting background one, and background jobs never take the last thread, so an interactive one finds a thread even while syncs and reloads wait in the rate limiter. Dropping the returned future before the job starts skips it; once started it runs to the end and its result is dropped.
  - A wait measured in minutes (the browser sign-in, "Sign in again…", an update's download) gets a thread of its own (`io::run_on_own_thread`), never one of the four.
  - In tests, `SessionScope::for_tests` runs calls inline, and the cache worker too: GPUI's test executor doesn't wait for threads of ours.
  - The exceptions: before the event loop starts, `main` claims the instance (a second copy must exit before it opens anything) and reads the preferences, because the first frame needs the theme.
- `cover_pipeline/`: covers (and avatars) from URL to GPUI image. `CoverService` (re-exported by `app_state`) is its global, for the whole run.
  - Covers are GPUI `Asset`s at three heights: `CoverThumbnail` (144 px) for xs and sm covers and md avatars, `CoverMedium` (288 px) for md and lg covers and the author page's xl photo, and `CoverImage` (600 px) for the detail cover (xl and xxl: the xxl cover is 600 device px at desktop scale 2 and interface scale 1.25); `CoverFile` is an SVG avatar's file. Every draw goes through `load_cover(url, height, ..)` or `cover_file`, which stamp the cover as drawn (`usage.rs`) before `use_asset`; never call `use_asset` on a cover asset directly. `Cover::thumbnail` picks the height by size (`CoverSize::image_height`), so each is sharp up to 2.4x scale; an lg cover from the 144 px thumbnail was enlarged on a 1.5x monitor.
  - Nothing blocks a GPUI thread (`queue.rs`). Downloads run on four `cover-download` threads: on GPUI's background pool (as many threads as cores) a few stalled 30 s downloads held every thread and sync, search and writes waited. One download per URL however many sizes ask, and a URL nobody waits for any more by its turn is skipped: releasing an asset drops GPUI's load task, which closes its channel. A row scrolled away is only served later until it is released past the budget. Decoding, scaling and saving copies run on one `cover-decoder` thread: decoding on GPUI's 16 pool threads bloated glibc's per-thread malloc arenas (62 MB versus 495 MB on a 442-cover benchmark), so keep every large decode, conversion and copy write there. Both queues serve the cover drawn most recently first (a cover scrolled back into view moves up), and the startup tidy's jobs last.
  - Memory: past a budget (`usage::THUMBNAIL_BUDGET`, 600 + 32; `MEDIUM_BUDGET`, 150 + 16), the loaded thumbnails and medium covers drawn longest ago are released with their textures (`CoverService::release_unused`, deferred from the draw that went past it), by rank, never by age: a view that sits still doesn't draw again. A release then redraws every window (`refresh_windows`): a cached view that sits still shows its covers without stamping them, so it draws them again (reloading one it still shows) and its covers count as drawn now. Drawn again, one loads from its saved copy. The book view still releases its similar books' lg covers itself (`release_cover_medium`), and the pane its detail cover (`release_cover_image`). Both keep the usage map in step, as does `retry_failed`: `release` calls `fetch_asset`, which would start a load for a cover the map wrongly thinks loaded.
  - Decoding refuses images over 12,000 px a side or 32 million pixels, from the header, and a scaled copy is at most twice as wide as its height (`scaled_size`). Scaling uses `fast_image_resize` (bilinear, the same Triangle filter `image` used). `cover_quality_tests.rs` checks the output against `image`'s resize, and that a JPEG thumbnail stays above 32 dB PSNR; set `COVER_QUALITY_DIR` to run it over a real cover cache.
  - The scaled copies are the cache (`scaled.rs`). A download is decoded once into every size (`SCALED_HEIGHTS`), saved in `covers/scaled/v<N>/` (opaque copies as JPEG q92, thumbnails included; a cover with transparency as lossless QOI of its BGRA pixels), synced, then the download is deleted; it stays only if saving failed. On 150 real covers a JPEG thumbnail took 8.9 KB against 30.1 KB as QOI (PSNR 38.4 dB on average, 33.2 at worst). Older caches still have QOI thumbnails, read as before. A cache made before the 288 px size has no download left to decode, so `scale_from_larger_copy` scales the missing size from a larger copy, with no download. A relaunch reads the copies and decodes nothing; `read_copy` is the one reader of copies (it deletes a copy that doesn't read, a truncated JPEG say, or is wider than the cap, so a copy on disk is usable: the downloader skips a cover with every copy).
  - Bump `SCALED_VERSION` when the decode output changes. Older versions' copies are rebuilt from (the largest older copy, decoded), lazily as covers are shown and eagerly by the startup tidy, which then deletes them, so a bump downloads nothing again, except a size larger than every older copy: an older copy is never enlarged (v1's 480 px detail copy makes v2's smaller sizes, and the 600 px one is downloaded when shown), unless it is shorter than its height, so the whole original. Heights an older version saved and this one doesn't are listed in `EARLIER_HEIGHTS`. Don't bump for a change to how copies are stored: rebuilding assumes the same encoding.
  - A download that doesn't decode is deleted, so the next try (after a sync) downloads it again; the second time it is kept and counts as unsupported, which `retry_failed` doesn't retry. The core refuses image types the app can't show (AVIF, say) before writing (`Error::Decode`), also unsupported. SVG avatars (`cover_file`) never reach the decoder and keep their download.
  - `tidy_cover_dir` runs on its own thread at startup, off the first screen's path. It deletes temporary files over an hour old, files loose in `scaled/` (an earlier layout) and downloads that have every copy. It converts the other downloads over an hour old (earlier builds kept them; SVGs excepted) by decoding the download itself into the sizes it lacks (`Decoding::convert`), rebuilds from older versions, then deletes them, each job one at a time and awaited, so a cover being shown waits behind one job at most. Then, past `COVER_CACHE_LIMIT` (256 MB), it deletes the files used least recently, down to three quarters of it; the decoder checks the limit again after every 16 MB of copies saved. Reading a copy sets its modification time, at most daily (`mark_used`), which is what "used" means there (the cache is on btrfs with `relatime`).

- `library/model.rs`: `LibraryModel` is the one entity every library view reads.
  - It loads the cache first, then syncs page by page. With nothing cached, a first sync that fails leaves the library never loaded (`is_loaded` false, `load_failure` says why; the pages it showed so far are dropped), and Home, Stats, Series and the shelves show the failure with "Try again" (`library::load_failed`, a `ui::LoadFailed` filling the region) in place of their empty states; the sidebar's shelf counts read "—" and the shelf's header has no count until it loads. Coming back to the window syncs again once the last sync started 15 minutes ago or more (`sync_if_stale`, also after a failed one), so changes made on the website or a phone show without Refresh.
  - A sync whose entries equal the ones shown (`collection::same_entries`, in any order) keeps the revision, so Home, Stats, the shelves and the series aren't worked out again and the goals aren't fetched again. The cache is still written (diffed): a first sync filled the entries page by page, so they match but weren't saved.

  - The cache is checked against the account once the sync's `me()` answers: a library cached for another account is dropped from the screen and the cache (companions too), and the sync fills it again; `AccountChanged` tells the other models to drop what they showed from it (`Resource::forget_from_disk`). Until then `user()` may be the cached one; anything acting on the account uses `verified_user_id()` (or `me()`), as "Sign in again…" and the reviews fetch do.
  - Every library write goes through `LibraryModel::write(LibraryWrite::entry(id, kind, title, call))` (or `LibraryWrite::add`), which owns the lifecycle: one write per entry at a time (a second gets `STILL_SAVING` as a notification), the call at interactive priority, applying what it returns (`Written`: an entry, `Removed`, a review), and a failure as a notification titled `title` (`reported_by_caller()` for the progress dialog, which says it next to its field). The write in flight holds its task, so ending it, on success or when the session ends, is one removal; the model owns it, so closing the view that asked doesn't cancel it. The returned future is for the caller's follow-up (`WriteOutcome`); dropping it changes nothing. `library/writes.rs` has the ones several views make.
  - Writes return the full entry, which replaces the local one and is upserted into the cache.
  - A sync re-applies the writes it may not have seen: those made while it ran and in the 30 s before it started (`collection::REAPPLY_WINDOW`, `RecentWrites`), since Hardcover can answer a read right after a write with the old row. A synced row with a later `updated_at` than the write's is newer, and stays (`collection::merge_sync`). A write during a first sync (pages shown as they arrive) is shown once.
  - Reviews are not part of the sync (review text can be long). The model keeps them in a `Resource` per entry: fetched when a book view shows the entry (`request_review`), kept for the run, and stale after each sync, so only the view shown fetches its review again (the workspace revalidates the visible views when a sync ends); a hidden one waits until it is shown. A review write's response replaces it (`Resource::set`), so a fetch that started before the write is dropped. The app writes only `review_markdown`: a review written on the website (only `review_slate`, with Hardcover's plain `review_raw`) is shown read-only, with a link to edit it on Hardcover.
- `library/filter_bar.rs`, `library/shelf_tags.rs`, `library/tag_filter.rs`: a status shelf's genre and mood filter (`hardcover-design`, The filter bar). Every status shelf has it; it hides without `read:catalog`, and its picks then count for nothing.
  - `ShelfTagsModel` holds each book's `BookTags` (`Client::book_tags`) in a `Resource` per book, saved in the library cache (`resource::saved`, kind `book_tags`). It asks only for the shelves shown this session: a shelf's books when it is shown (`Demand::Shown`: never asked, stale or failed), its stale ones when the window becomes active, every shown shelf's on Refresh and after "Sign in again…", and 2 s after a sync or write changes the books on those shelves only the books it doesn't know yet (`LibraryFollow`, `Debounce`), dropping those that left the library. A book Hardcover leaves out is known to have nothing. A failed batch keeps its books' copies; `ShelfTagsModel::shelf` says where a shelf stands (`ShelfTags`: loading with nothing known, failed with nothing known, or ready with a failure beside it) and `retry` is "Try again". What the filter needs of a book (`tag_filter::BookFacts`: its genres and the moods of its mood line, through `tags::has_mood` only) is worked out once as its tags land. A shelf costs one background request per 100 books (`BOOK_TAGS_BATCH`) when it is first shown in a run, and again only as its books go stale (30 minutes); its saved copies show meanwhile.
  - `tag_filter.rs` (pure, tested): `TagPick` (one genre, by `genre_key`, with the name its chip showed, and one mood; a book must have both; a press on the selected chip clears it), `facets` (each row's chips: the shelf's own tags ordered by the whole shelf's counts, ties by name or `Mood::ALL`'s order, so the rows don't reorder as the reader picks; each count under the other row's pick; disabled at 0 unless selected; a pick the shelf lost stays offered at 0; the genre's name is the spelling most of the shelf's books use; `unfindable`, the books with tags known but no genre and no mood line), `fit_row` (as many as fit, then "More" with the rest; a selected chip that doesn't fit in its place goes first; the first chip is kept and cut) and the empty state's and foot's words.
  - `FilterBar` is a view inside the cached `ShelfPane`, which observes it. It keeps the picks per shelf for the session, measures its own width as it is laid out (the list is resizable), and tells `LibraryView` of a new pick (`PickChanged`); the shelf filters its rows by the pick, the text filter and the sort together (`RowsKey` holds the pick, and the tags' revision while a pick is set), keeps a selected book that still matches and otherwise selects the first match. The title reads "2 of 8" with "Clear filters" while either filter is set; "No matches" has "Clear filters" too; both clear the chips and the text and give focus to the list. A press from the keyboard keeps focus on its chip, and a chip that leaves its row as it is pressed hands focus to the row's first. Each row is one Tab stop with the arrows inside (`ui::chip_keys`, as a book's genres are), "More" included.
- `resource/`: data fetched for the session, kept per key, and when it is fetched again. A `Resource<K, V>` (`resource/mod.rs`) holds per key the value, a `Stamp` taken when its request *started*, the request in flight, a write generation and why the last fetch failed; callers only ask (`request`, with a `Demand`), and it decides:
  - Never fetched, or stale: fetched again while the old value stays on screen. Stale means older than `STALE_AFTER` (30 minutes), or asked for before the last Refresh (`refresh_all`, Ctrl+R). A request in flight is asked for once however many views want it; one that started before a Refresh is started again, so Refresh never finds a request it can't count. Ages are wall-clock (`SystemTime`), as is `LibraryModel::sync_if_stale`'s: `Instant` stops while the computer sleeps. A clock set back counts as stale.
  - A failure keeps the value and counts as a try: it is tried again only when shown (`Demand::Shown`: opened, shown again, Refresh) or asked for ("Try again", `Demand::Now`), never because the window became active (`Demand::Active`), so being offline doesn't send a request (or flash a placeholder) on every return. `error` is a first failure, shown in place of the value; `failure` also one beside a value; `more_error` a later page's (`extend`).
  - A write (`set`, `update`, `note_write`) bumps the key's generation: a fetch that started before it is dropped when it lands (`Landing::Dropped`), and not fetched again at once (Hardcover can answer a read right after a write with the old row); owners that need it load again after a delay (`Debounce`). An equal result only renews the stamp (`Landing::Same`), so lists built from it aren't rebuilt.
  - Nothing is sent without the resource's scope (`SessionScope::allows`), and a failure for want of it records the scope as refused. A result landing after the session ended is dropped.
  - `request_many` asks for several keys in one request (`Batch`: each found or failed); the series tracker asks so.
  - `catalog.rs`: `Catalog`, the session's catalogue, one `Shared` entity per kind (book details, similar books, other readers' reviews, editions, series and author pages, Trending's periods (`TrendingBook`s), a list's books, a vibe's books, a tag's books keyed by `TagBooksKey` (`request_tag_books`, `more_tag_books`)), made in `Workspace::new` before the views and found with `Catalog::global`. Every view asks it (`request_*`) and subscribes to `SharedChanged` for the ids it shows, keeping only UI state, so the book page opened from a pane shows the pane's details, reviews and similar books at once, with no request. Paged values are `Paged` (`next_offset`, one less for every row taken off since) and `ReviewPages`.
  - `follow.rs`: how models follow the library: `LibraryFollow` reports a key worked out from it (a revision, its series) first when the library loads and then only when it changes, never for a running sync's pages; `Debounce` runs one reload after a run of changes.
  - `saved.rs`: resources kept in the library cache between launches (the goals, the lists, the list membership index, the upcoming books, each tracked series and each shelf book's tags), in its companions table (`LibraryCache::save_companion`), one row per key, written through the cache worker. They show at once at the next launch (`Resource::hydrate`, never over a value of this run), offline too, and are fetched again as stale; sign-out's clear and an account mismatch remove them.
  - Views can't tell whether they are on screen, so `Workspace::revalidate_visible` asks the visible ones (the top page and its pane, else the destination's catalogue content) on Refresh, when the window becomes active, when a sync ends (it makes the own reviews stale), and when a page or destination is shown again. Each view's `revalidate` asks its resources, which decide, so asking is cheap. Search asks its pane only on the Books tab.
  - The book view keeps its settle and stagger delays itself (details, the own review, similar books, reviews, `SETTLE`); the reviews don't wait on the details. A series, author or Trending page keeps the selected book per page (`book_list::PageRows`): another page starts empty and at the top, Back finds the book selected there, and a page fetched again replaces its rows with `book_list::replace_rows`, which keeps the selected book; the pane then gets the same book with newer facts, which `set_subject` takes without resetting anything.
- `notify.rs`: `notify_failure` and `notify_outcome`, the one way a background write started from a dialog or control (list and goal writes) says it failed, titled with what couldn't be done, and, when the change isn't visible, that it worked.
- `fonts.rs`: bundles the app's fonts and sets the interface font on the theme: Inter (the interface), Literata Text (the 12 pt cut, family "Literata") and Literata Display (the 36 pt cut, "Literata 36pt") for the book, and Vazirmatn for Persian and Arabic under both. `FACES` is the one list, registered and tested.
  - `prewarm` warms GPUI's font caches on a thread of its own while the window opens (GPU setup takes ~300 ms there): the first time a family is shaped at a weight and style, cosmic-text ranks every installed font against it, opening the file of each whose weight differs (834 fonts on the owner's machine), and the first frame used to pay for that. Measured on the real app (exec to a settled Home, paired against the previous build): 7 to 13% faster. Add a weight or style the first screen uses there.
  - Every face must be static. GPUI's Linux text system draws only a variable font's default instance, so with a variable system font (Adwaita Sans) every bold run rendered regular. A test rejects variable faces.
  - Persian and Arabic fall back to Vazirmatn because it is named (`FontFallbacks`): by each type role, on the shell's root, and by `WrappingText` (dialogs and popovers don't inherit from the shell). GPUI uses a family, primary or fallback, only if it maps "m", so a font without Latin (Noto Naskh Arabic) can't be used.
  - Each family lives in `assets/fonts/<family>/` with its OFL `LICENSE.txt`; `package.sh` installs every one as `<family>-LICENSE.txt`.
- `bidi.rs`: `WrappingText`, for catalogue and user text that may wrap (titles, names, descriptions). GPUI's Linux layout draws wrapped right-to-left text (Persian, Arabic) mostly outside its box; a line that doesn't wrap is drawn correctly. GPUI also lays every run out as if the line read left to right, so punctuation and brackets at the edge of a Persian run land on the wrong side. So right-to-left text goes through the bidirectional algorithm (`unicode-bidi`, brackets mirrored with `unicode-bidi-mirroring`): it is cut into pieces where the line may break, each piece into segments that read one way only (a run of letters, a Latin run such as "Harry Potter", one punctuation mark), laid out in reversed flex rows. It goes by grapheme cluster (`unicode-segmentation`), so an emoji with its variation selector, skin tone or joiners, or a letter with its marks, is never split or reversed apart, and a cut never falls inside one; left-to-right text takes GPUI's own path. With `.width(..)` it breaks both directions into lines itself, between words (a Latin phrase inside right-to-left text too, at its spaces), the last clamped line ending in "…", and a word too long for a line cut short with "…" rather than split (Chinese and Japanese, which break anywhere, go on over the next line) (cloth covers, cover shelves: GPUI's wrapping in a narrow box starts the next line with a space and cuts words). Use it instead of a plain string child wherever such text can wrap. Single-line `truncate()` text stays in its box but still gets a Persian run's edge brackets wrong, so `TextButton` (titles in rows) sets a right-to-left label through it, clamped to one line. It also names the Vazirmatn fallback for the family it inherits, and `.centered()` centres its lines (the cloth cover). Markdown reviews and text fields still use GPUI's layout. Where right-to-left text sits is a design rule, in `hardcover-design`.
- `text.rs`: matching text as a reader types it. `fold` lowercases, drops accents, harakat and other marks, writes Arabic letter forms as Persian does (ي ى → ی, ك → ک), Persian and Arabic-Indic digits as ASCII, and composes the result (NFC); `search_words` and `indexed_words` cut a query and a title into words, where a word with a zero-width non-joiner matches with it, without it or with a space. Library search, a shelf's filter and the Series filter all match through them. `ascii_numerals` reads Persian digits, `٫` and `٪` in number fields (the progress dialog).
- `dates.rs`: every calendar day the app works out. Hardcover's timestamps are UTC; `local_day` gives the day one falls on here, and `today` is today here. Never call `date_naive()` on a UTC timestamp. Views read today as they render (caches key on it), and the workspace's 30 s clock re-renders, and refreshes the whole window when the day changes (the cached views draw only when they change), so a window open across midnight moves to the new day.
- `star.rs`: the rating star, a rounded solid SVG (`assets/icons/star.svg`) used instead of Lucide's. Its colours are tokens: `design::colors(cx).gold` (the user's own rating only), `fg_muted` and `star_empty`. Which star gets which colour is in `hardcover-design` (Stars).

A chip that opens a page is pressed (`TagChip::opens(page)`; `TagChip::genre_page(name)` opens the genre's `Page::Tag` when `tags::browse_genre` finds one, else it stays a plain genre chip): it hovers, takes focus and presses with Enter or Space, and is a `reveal::probe`, so a scrolling page keeps it in view; `.key(id)` names it when its text may repeat in a row (Discover's featured vibes). `TagRow` wraps chips 6 apart both ways (`s-6`: the header's genres, each tag group), and with `.keys(id, &chip_keys)` makes its pressed chips one Tab stop (`ui::chip_keys`); `TagGroup` is one group of the Tags block, its label 6 above its row; `tag_groups` stacks them 16 apart. `FilterChip` (`chip/filter.rs`) is a shelf's filter chip: `FilterChip::genre` (its icon) or `::mood`, the count after the name, `.selected` (the `selected` fill and a check in the icon's place), disabled at 0 unless selected (out of the Tab order), a toggle named "Fantasy, 5 books" to a screen reader; `filter_chip_width` and `small_menu_button_width` are their widths as drawn, from the text shaped at the window's rem, for fitting a row. Use these, not `Tag` directly, for any new status or tag. How they look is in `hardcover-design` (Chips).
  - `chip/genre.rs`: `genre_icon(name)`, pure and tested. The name is normalised to lowercase words (`&` is "and", apostrophes go, other punctuation separates); a whole-name match wins, then the first genre in `GENRES` whose name appears as whole words, so the specific genres come first ("Non-Fiction" before "Fiction", "Science Fiction" before "Science"). No match, no icon (Persian names, "General"). A new icon goes into `GENRES` and `icons::ExtraIcons` (unless the kit's defaults have it); a test loads each through `AppAssets`, and another checks every genre in the demo catalogue.

## Hardcover API quirks the code relies on

- Status ids: 1 Want to Read, 2 Currently Reading, 3 Read, 4 Paused, 5 Did Not Finish, 6 Ignored.
- Setting a rating without a status moves the book to Read. `set_rating` therefore takes a `keep_status` and resends the current status. `set_review` and `delete_review` do the same. Verified live: a review sent with the current status leaves the status alone and starts no read.
- Review arguments (`review_markdown`, `review_slate`, `review_has_spoilers`, `reviewed_at`) need `write:reviews`, which gates only those arguments, not an operation. `UPDATE_USER_BOOK_REVIEW` and `DELETE_USER_BOOK_REVIEW` write them out instead of passing them in `$object`, so the scope test sees them. `UserBookUpdateInput` has no `review_raw`. Hardcover ignores `null` or `""` for `review_markdown` and `null` or `{}` for `review_slate`: none of them clears a review. Writing an empty Slate document to `review_slate` does (`review_markdown` becomes null, `review_raw` empty, `has_review` false), so `delete_review` sends one. `reviewed_at` can't be cleared, and means nothing once `has_review` is false. Saving `review_markdown` fills `review_raw` and `review_slate` too. Reading other users' reviews: see the next bullet.
- Other readers' reviews are `user_books` rows with `has_review` true; `BOOK_REVIEWS` leaves out the user's own with `user_id: {_neq: $me}` and orders by `likes_count`, then `reviewed_at` (nulls last), then id. The scope map grants `user_books` and `user_books_aggregate` through `read:library`, but `read:social` is what covers other users' content, so the feature is gated on `READ_SOCIAL`. Verified live (read-only): `review_raw` is plain text with `\n\n` between paragraphs, and some are in Persian; `rating` is a float or null; `reviewed_at` is a timestamp or null; `user.name` can be `""`; `user.cached_image` is `{url, color, width, height, id, color_name}`, where `url` is a Hardcover asset (SVG, PNG or JPEG) or a default avatar. Profiles are `https://hardcover.app/@<username>`. Unverified: that `cached_image.color` is a hex colour (anything else falls back to the kit's initials).
- Reading an entry right after a write can return stale data. Use the entry from the mutation's own response, and refetch only when it is missing.
- Progress is `progress_seconds` on a read whose edition is an audiobook (`reading_format_id` 2) and `progress_pages` on any other (the official SDK's `ReadingFormat`: 1 physical, 2 audiobook, 4 ebook; 3 is unused), whichever lengths the edition lists. A library checked read-only had 27 audiobook entries: 23 with `audio_seconds` and no pages, 4 with neither; none had both.
- Moving a book to Currently Reading starts a new read. A progress update with no open read moves the book to Currently Reading first; if the progress then fails, `update_progress` still returns the moved entry (`ProgressChange::progress_left_out`), so the UI shows the read that now exists and a retry writes to it.
- Dating a status change (verified live, 2026-11-21, on a book not in the library, restored): `user_date` on `insert_user_book`/`update_user_book` dates the read the change starts (Currently Reading: `started_at`) or finishes (Read: `finished_at`). Left out, the server uses today in the account's time zone (`users.timezone`, UTC without one; the official SDK's spec says so), which needn't be this computer's, so `set_status` and `add_to_library` send today's local date with those two statuses (`status_fields`). `user_start_date` is ignored with Currently Reading and, sent with Read, leaves the open read unfinished: never send it. `action_at` doesn't date the read. A mutation's own payload right after a status change can show the old dates; read back to check.
- `insert_user_book` for a book that already has an entry (verified live, 2026-11-21): no error and no second row; it returns the existing entry's id and overwrites its status (an Ignored entry became Want to Read).
- An entry can have many reads. The current one is the newest unfinished read, else the most recently finished: a past read added later gets the highest id. `update_progress` picks its read the same way: the progress context fetches every open read and sorts them with `read_order` (`ProgressContext::sort_reads`), so it writes to the read the UI shows. Changing the edition moves an open read at the same percentage, but always short of the end (even from 100%), since progress at the end finishes the read.
- `edition_owned(id)` takes an edition id and only adds it to the user's Owned list (creating the list the first time, and posting to their feed). The Owned list is the user's `lists` row with slug `owned`, as the official SDK (github.com/hardcoverapp/hardcover-sdk) finds it. Taking an edition off is `delete_list_book(id)` (`write:lists`), which takes the `list_books` row id, not the book's; reading the list needs `read:lists`, and `user_books.owned` does not follow the list. The app counts a book as owned when any edition of it is on the list, and turning Owned off removes every one.
- Lists: `lists` returns at most 100 rows per request and `list_books` 1,000, so both are keyset-paged. Unranked lists usually have no `position`, so list books are ordered by position, then id. Verified live: adding a book that is already on a list returns the existing row, and an empty description clears it. Whether `update_list` keeps fields left out is unverified, so `Client::update_list` reads the list by id just before writing and sends it back with only the fields the user edited changed (`ListEdit::between` the list as shown and the dialog's draft); the rest (`default_view`, `featured_profile`, `url`, the raw `privacy_setting_id`, and the unedited name, description and ranking) goes back as Hardcover has it then, so a change made on the website since the app loaded the list stays. `insert_list`/`update_list` return `errors` (a list); `insert_list_book` and `delete_list_book` have no error field, so a missing id is the failure.
- Goals: `metric` is `book`, `page` or `hour`. Hardcover dates its own year goals from Jan 1 to Jan 1 of the next year (seen live: "2026 Reading Goal", Jan 1, 2026 – Jan 1, 2027), so `format::goal_year` counts that as a calendar year, as well as Jan 1 to Dec 31, and `Goal::last_day` ends it on Dec 31: on New Year's Day it has ended. For hour goals `goal` is in hours but `progress` in seconds; `Goal::progress` is converted to hours. `update_goal` takes a whole `GoalInput` (fields left out are not kept), so `Client::update_goal(id, edit)` reads the goal by id just before writing, applies the caller's edit to that copy, and sends it whole, `conditions` and the raw `privacy_setting_id` included; it refuses one whose conditions hold a field it doesn't know or that has no description (`description` is `String!`). The mutations return `errors` (a list), not `error`. `delete_goal` answers a successful delete with `id: null`, so only `errors` means it failed. A goal created without `privacy_setting_id` gets the account default. Progress updates by itself as the user reads (`update_goal_progress` exists but the app doesn't call it).
- Upcoming books: one `book_series` query with `series_id _in` the library's series and `book.release_date _gt` today (`read:catalog`) returned 27 rows for 210 series in about 1 s, live. Merged duplicates (a non-null `canonical_id`) come too, so it filters them; a book in two series (a series and its reading order) has a row for each, merged by `upcoming_books`. Positions may be fractional or null, and far dates are placeholders (Jan 1, Dec 1). An author-based variant (`contributions` by `author_id`) found nothing and is unverified; the app uses series only.
- Vibes (verified live, read-only, 2026-11-22 and 23): a user's system vibes are `vibes` rows with their `user_id` and `vibe_type` 1 (Recommendations: 250 ranked ids in `cached_book_ids`) and 3 (Top Picks: 35); type 2 ("Because you read") was absent, and 0 is a custom vibe (Supporters only). `books_generated_at` is UTC without an offset. A vibe is built again only when the user opens Discover or the vibe on hardcover.app at least 24 h after its last build: neither a visit sooner, nor 24 h passing without a visit, nor `ensure_system_vibes` (which returned the existing ids), nor a no-op `update_vibe` rebuilt one. Featured vibes (`featured: true`) of other users can be read. Recommendations include books already on Want to read (48 of 250), and none Read or Currently Reading.
- Excluding a book from a vibe is `update_vibe(id, object: {vibe_exclusions_attributes: [{excluded_type: "Book", excluded_id}]})`. Verified live by the owner (2026-11-23, on a book not in the list): `exclude_from_vibe`, which reads the vibe and sends its title, description and `privacy_setting_id` back with the exclusion, is accepted (`errors: null`) and leaves the vibe's fields and books as they were; the list changes only at its next build, hence the app hides the book itself. Not checked: whether `update_vibe` keeps fields left out. The exclusions can't be read, and there is no way to undo one from the app. A vibe's page on hardcover.app is `https://hardcover.app/@<owner>/vibes/<slug>` (the owner's Recommendations: `/@<username>/vibes/recommendations`).
- Tags (verified live by the owner, read-only; the site totals were read 2026-11-22, the catalogue counts in `tags/fixtures` 2026-11-23): `taggable_counts` holds a book's exact votes per tag (`books_by_pk { taggable_counts(where: {tag_id: {_in: [...]}}) { tag_id count } }`, the same on `books(where: {id: {_in: $ids}})` for a batch); `cached_tags` keeps only the top few. Of Hardcover's many mood tags only 14 count (`tags::Mood`): below them use falls off a cliff and the rest is noise. Pace ids: medium 182, fast 188, slow 195. Character tags (category "Tag"): Plot driven 208, Character driven 194, A mix driven 183; Loveable 185 / Unloveable 197, Strong 184 / Weak 189 Character Development, Diverse 186 / Not Diverse 196. A tag's books, ranked: `taggable_counts(where: {tag_id: {_eq: $tag}, taggable_type: {_eq: "Book"}, book: {canonical_id: {_is_null: true}}}, order_by: {count: desc})` (relaxing gives Legends & Lattes, 186 votes, then A Psalm for the Wild-Built, 96). Rank by `count`, never by `users_count`, which brings the same blockbusters whatever the tag. A second tag narrows it with `book: {taggable_counts: {tag_id: {_eq: $other}, count: {_gte: 5}}}` (`tags::MIN_OTHER_TAG_VOTES`; at 3, 1984 came up as Fantasy, though Fantasy is not among its genres; 5 leaves it out and keeps The Hunger Games and Mexican Gothic. Paged with a tie-break on `taggable_id`, checked live: two Fantasy pages, no overlap). Genres are free text with duplicates ("Sci-fi", "Science Fiction", "science-fiction", "Science Fiction & Fantasy"; "Non-Fiction" and "Nonfiction"; case variants), hence `tags::genre_key`.
- Series follows (verified live 2026-11-23, restored): rows of the generic `follows` table (`followable_type` "Series", `followable_id`, `created_at` in UTC without an offset); a plain read returns only the caller's own rows, under `read:social`. `insert_follow(followable_id, followable_type: "Series")` and `delete_follow(...)` need `write:social`. Following again returns the existing follow (same id, no error); unfollowing a series not followed answers `success: true`; an unknown series is `id: null` with `error` ("Series with id … does not exist"). Neither posted to the feed. A follow of a merged duplicate counts as its canonical series (`wire::followed_series`).
- Search has a 2 s server timeout. The `_like`, `_ilike` and regex filters are disabled.

## CI and releases

- `.github/workflows/ci.yml` runs on pull requests, on pushes to `master` and weekly:
  - fmt
  - clippy with `-D warnings`, and the tests, as two parallel jobs
  - `cargo deny` (`deny.toml`)
  - cargo-deny and actionlint are downloaded by version and checked against a pinned SHA-256 (from their releases' own checksum files); bump each version and its checksum together.
  - desktop-entry and metainfo validation
  - ShellCheck over `install.sh`, `packaging/linux/`, `ci/` and `scripts/`, `scripts/release-test.sh` (the release script's network handling, offline, with a fake `gh`) and `ci/apt-get-test.sh` (the apt wrapper, with a fake `apt-get`), then `install.sh` against the latest published release: it must install it, and refuse that tarball modified or renamed to another version
  - actionlint
- Clippy and the tests run in an `ubuntu:22.04` container, the same one the release builds in. `ci/install-build-deps.sh` holds the system packages; it is the single list for both.
- Every job in `ci.yml` and `release.yml` has a `timeout-minutes`, a few times its usual length, so a hung network wait fails the job (and `just release` with it) instead of holding it for GitHub's six hours.
- Every apt install in CI goes through `ci/apt-get.sh install [--update] [--download-only] <packages>`, never `apt-get` directly. The mirrors sometimes stall or trickle, which apt's own timeouts (inactivity only) don't catch: on 2026-11-23 a two-package install sat in `apt-get update` for 22 minutes. The wrapper refreshes the lists and downloads the packages each within a generous time limit (8 and 15 minutes: a slow mirror often finishes), tried three times, and drops a connection silent for 10 s (apt waits 120: silent connections to `archive.ubuntu.com`, not slow transfers, are where the time went), then installs offline with no limit (dpkg is never killed). Without `--update` it first tries the lists already there and refreshes them only if that fails.
- `.github/actions/setup-rust` sets up every build job. Its caches are saved only from `master`; other branches restore them.
  - apt: the Ubuntu mirrors sometimes stall for minutes, so the package lists and `.deb`s are cached under a monthly key. On an exact hit, CI jobs install without `apt-get update`. The release always updates (`fresh-packages: true`), so its packages are checked against freshly signed lists.
  - zstd is installed after the apt cache is saved, so that cache stays gzip; it is restored before zstd exists. The cargo caches (`Swatinem/rust-cache`, one per job) then use zstd.
- The toolchain is pinned in `rust-toolchain.toml`. Bump it on purpose, and fix any new clippy lints in the same commit.
- Actions are pinned to commit SHAs; Dependabot updates them.
- **To release:**
  1. Bump `version` in `crates/app/Cargo.toml`.
  2. Add a `<release>` to `packaging/linux/io.github.alisayyah.HardcoverDesktop.metainfo.xml`.
  3. Push a `vX.Y.Z` tag.

  `just release <patch|minor|major|X.Y.Z>` (`scripts/release.sh ship`) does all of it. It asks once, then:
  - bumps `origin/master` in a temporary worktree (never the current checkout): the version, `Cargo.lock`, and a `<release>` dated today;
  - pushes `release-X.Y.Z` and opens the "Release X.Y.Z" PR, assigned to the user, listing the commits since the last tag;
  - waits for its CI run, then squash-merges it as "Release X.Y.Z (#N)" and deletes the branch;
  - waits for CI on the merge commit, then tags that very commit (never whatever `master`'s tip is by then) with the annotated tag `vX.Y.Z` ("Hardcover Desktop X.Y.Z") and pushes it;
  - follows `release.yml` until the GitHub release exists, and prints its URL.

  It refuses a version that isn't newer than the current one and the latest tag, and a release with no commits since the last tag. After a failure (red CI, say), fix it and run `just release` again with no level: it resumes an open `release-*` PR (or a pushed `release-*` branch whose PR wasn't opened), a bump on master that has no tag yet, or a tag that hasn't been published. Tags count as they are on the remote: a local tag left by a run that stopped while pushing it is pushed as it is, if it is on the bump commit. `--yes` skips the question; without a terminal it is required.

  It rides out a flaky network. Every read from GitHub (gh or git) goes through `retry`, which tries again for about three minutes when the error is the network's (`transient`: gh's `Get "https://…": …`, git's `unable to access`, a 5xx or a rate limit), and never when it is an answer (a 404, "release not found"). Every change (pushing the branch and the tag, opening and merging the PR) goes through `write`, which, when it fails, first asks whether it went through anyway (the PR is open or merged, the remote tag peels to the commit), and tries again only if not; each is safe to send twice. A CI run is followed by polling `gh run view`, not `gh run watch` (which ended 0.4.0's run at its first dropped connection, saying the build failed), so a run that failed and a network that did are told apart; a wait gives up after 15 minutes' worth of failed polls. Whenever the network stays down it says so (`lost_contact`) and stops in a state the next run picks up. `scripts/release-test.sh` covers this against a fake `gh`; add a case there when you change it.

  The steps also run on their own:
  - `just bump <level>` edits this checkout and commits nothing.
  - `just release-pr <level>` only opens the PR.
  - `just release-tag` only tags the bump commit on `origin/master` (the newest on its first-parent history that added the version's `<release>`; CI on it must already have passed; it asks first) and follows the release build. Commits after it are not in the release. Resuming a bump already on master tags it the same way.

  It merges only a PR from this repository (never a fork's), into master, that is one commit on master's current tip and exactly the bump: `check_bump` runs the parent's files through the same filters the bump uses (`bump_manifest`, `bump_lock`, `bump_metainfo`: the first `version =` of `crates/app/Cargo.toml`, the `hardcover-desktop` version in `Cargo.lock`, a dated `<release>` first under `<releases>`) and requires the result to equal the commit's, with no other file changed. Anything else stops it before CI is even awaited, and it checks again after CI, before merging. If master has moved since the PR was opened it refuses (the release would ship changes the PR doesn't list): close the PR and run it again. After merging it tags only if the merge commit's tree is the PR head's, the tree CI tested. The bump commit that resuming or `release-tag` finds gets the same `check_bump`. Keep the filters in step if the bump ever changes more.

  `release.yml` checks that the three versions agree and builds with `--profile dist` (thin LTO, stripped). The build job, in the `ubuntu:22.04` container, packs the tarball (`packaging/linux/package.sh`) and repacks it as an AppImage (`package-appimage.sh`, with linuxdeploy and the AppImage runtime pinned by release and checksum). The AppImage embeds the standard update information (`gh-releases-zsync|AliSayyah|hardcover-desktop|latest|hardcover-desktop-*-x86_64-linux.AppImage.zsync`) and comes with its `.zsync`, for AppImageUpdate and the like; the script fails if either is missing. On a tag, the publish job adds `install.sh` from its own checkout of the tag (not from the build job's artifact: the build runs every dependency's build script), signs the tarball, AppImage and `install.sh` (not the `.zsync`), verifies them, runs the installer on the signed tarball, and creates the GitHub release. Running it by hand builds the packages, unsigned, as workflow artifacts, without `install.sh`.

  `install.sh` (repository root, also a signed release download) installs the latest release, or a tarball given with its `.minisig`, into `~/.local`, checking the signature and its `file:` name as the updater does. The README's one-liner runs the copy published with the latest release (`releases/latest/download/install.sh`), never `master`'s. It installs as the updater does: under `flock` on the prefix, each file copied beside its destination and renamed, the binary last. It carries its own copy of the public key, as do `README.md` and `release-notes.md`; a test (`every_copy_of_the_public_key_is_the_release_key`) keeps them in step with `packaging/minisign.pub`.

## Self-update

The core side is `hardcover_core::update`; the app side is `crates/app/src/update.rs` plus the sidebar row in `shell.rs`.
- **When it installs:** the app checks `releases/latest` on GitHub. The first check also works out the install kind (`InstallKind::detect`, which reads the AppImage header and probes `bin/` and `share/`), on the background executor; nothing needs it sooner, since only a release a check found can be installed. It installs a release only when it runs from an unpacked release tarball (`<prefix>/bin/hardcover-desktop` with the desktop entry under `<prefix>/share`) in a writable prefix, as `install.sh` sets up, or from an AppImage in a writable directory. Other installs only announce new releases: packages, development builds, and files this user can't replace.
- **AppImage:** the runtime sets `APPIMAGE` (the file) and `APPDIR` (where it is mounted, or extracted with `--appimage-extract-and-run`). Everything an AppImage starts inherits both, so they count only when the app's own executable is inside `APPDIR`; otherwise an update could overwrite another app's AppImage (a terminal in an AppImage editor passes its variables on). `APPIMAGE` must also carry the type 2 magic bytes. Anything under an `APPDIR` that fails a check is announce-only, never a tarball. The update downloads `hardcover-desktop-<version>-<arch>-linux.AppImage` and its `.minisig`, writes it next to the running file and renames it over it, keeping its path and name. `main` sets the restart path to the AppImage file, because the executable inside it is gone once the app exits.
- **Trust chain:**
  - The minisign signature must verify against `packaging/minisign.pub`.
  - The signature's `file:` comment must be the file name (tarball or AppImage) for the advertised version and architecture, which stops replays of older signed releases. Keep the version in the release file names for this reason.
  - The version must be newer than the running one.
  - The archive's top-level directory must match the tarball name.
  - Only regular files under `bin/hardcover-desktop` and `share/` are unpacked.
- **Installing:** under the same `flock` on the prefix that `install.sh` takes (on the AppImage's directory for an AppImage), waiting up to a minute for another install. Each file is streamed into a temporary file (`.hardcover-desktop-update-*`) in its destination's own directory, so the rename stays on one filesystem even when `bin/` or `share/` links to another; only once every file is written are they renamed into place, the binary last, and the directories synced. A failure before then removes the temporary files and changes nothing. Temporary files are made only under the lock, so each install (and `install.sh`) first deletes any a crash left in the directories it writes.
  - A downloaded AppImage must carry the AppImage magic bytes.
- **Restarting:** `main` resolves the executable path before anything else and passes it to `set_restart_path`; for an AppImage, the first check replaces it with the AppImage file once it has detected one (a restart only follows an install). After an update, `/proc/self/exe` points to the deleted old binary. "Restart to update" asks first while a book view holds an unsaved review or notes (`drafts`: each `BookDetailView` registers a check when it is made).
- **Signing:**
  - `release.yml` signs in the publish job, with the `MINISIGN_SECRET_KEY` repository secret exposed to that one step only, then verifies with `packaging/minisign.pub`.
  - Never replace the key: installed copies trust only this one.
  - Never re-publish different bytes under an existing version. If a release goes wrong, release a new patch version.
- **Release notes:** generated changes come first, followed by `<!-- install -->` and `packaging/linux/release-notes.md`. The app's update dialog shows only the part before the marker, tidied (`update::release_notes`): each change keeps its title (no author or PR link), and the release's own bump, "What's Changed" and "Full Changelog" go.
